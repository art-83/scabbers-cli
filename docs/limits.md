# External prerequisites and current limits

This application is implemented and locally verified. That does not mean live support or a NOLA production-ready rollout has been exercised.

- Support handles objective Bug, Bug Crítico, Ticket, duplicate and cancellation routes. Duplicates require an open verified Bug; cancellation requires a real reason field, an exact allowed option and an available cancellation transition. Product/information handoffs keep the Report open and never create an RFC. Missing mappings or a verifiable Jira link block the dependent action; ambiguous behavior requires a private decision.
- Jira metadata, required fields, squad compatibility, issue relationships, credentials and exact transition names must match the actual project. Current development checkpoints expect available In Progress, Docs & Tests and Ready for Code Review transitions. An intermediate mandatory workflow step needs a verified mapping before the dependent mutation can run. The controller does not modify Jira administration.
- The installed catalog skills and repository test dependencies must be configured. Test commands are trusted local configuration, not text selected by a report or an engine. Budget enforcement is currently per Claude turn (USD 5) and a ten-minute process deadline; there is no cross-engine daily financial budget accounting yet.
- Engines were checked against the installed Claude Code 2.1.310 and Codex CLI 0.165.0. Their native sessions are real. External native authentication expiry and protocol/version changes can block a run.
- The JEV cutoff is the preserved provisional form-v0.6 threshold, not a calibrated success probability. Missing/invalid JEV responses never grant approval. Bug Fix and Development exclude provider-resource changes. Operational Tasks has its own plan/implementation approvals and executor; production behavior was not exercised in this delivery.
- Slack Socket Mode configuration exists, but its app-level secret was not available in the checked local environment/references. Live buttons/DM events additionally need the corresponding app configuration. The supported baseline is persisted polling, authenticated replies directly in the matching thread and numbered reactions where choices exist; no app token is extracted from browser/plugin internals.
- Historical support backfill begins at the persisted initial setup watermark. The current configured schedule is used for historical received timestamps; schedule-version migration and legacy-ledger import are intentionally not implemented.
- Native Claude browser capability is conditional on the official Chrome extension/native host, connected browser, approved domains and login. The final real read-only staging check read the home page with visible welcome text; earlier native domain-permission refusals were preserved as blocked checks. Codex browser stages load only the installed first-party cua_repl transport, retain native origin permission checks and expose a saved read-only connection diagnostic in Config. A real isolated CLI check subsequently read the staging login page with Codex after native permission was resolved; this establishes browser connectivity, not authenticated application E2E. Missing/refused browser access remains blocked, without a Playwright/CDP fallback.
- Staging exists for NOLA web development. Live GitLab/Jira configuration, exact deployed revisions, pipeline/deployment visibility, endpoint access and browser sessions still need real environment validation. No NOLA staging integration/deploy or customer task E2E was performed in this delivery.
- Browser-access retries return to E2E. Explicit revision decisions preserve previous evidence and start a new attempt with fresh review/publication approvals; one independent review is required per attempt.
- Persistence schema is version 1, without automatic migration from old Python data or incompatible future machines. Linux/Unix local runtime recovery is tested; Windows service/runtime support is not claimed.
- Local state/evidence can contain internal task data and test output. Keep its private directory on a trusted machine. JEV text is minimized/redacted and source excerpts secret-scanned, but automated detection cannot establish the absence of every domain-specific personal identifier; review data policy and configured exclusions before live intake.

- Development feature intake is implemented and locally tested, but no real feature-family delivery has been executed end to end. The feature JEV threshold is provisional. Workflow mappings are explicit by project/type; unmapped cards keep their status and receive comments. Jira search reveals only accessible issues; permission-hidden children cannot be independently proven absent. Analyses/JEV requests exceeding bounded budgets block for an owner decision rather than splitting or truncating the family.

- Engine model availability and supported effort depend on the installed client/account. Optional usage-limit fallback preserves structured context and each engine's own native session; it cannot transfer opaque native conversation history across vendors. Fallback behavior is covered with explicit protocol doubles, not a real exhausted subscription. Both unavailable engines leave a blocked checkpoint. Permission/authentication/spend-cap failures remain blockers.

- Processing now requires an open CLI panel. IPC owner loss stops the runtime and managed subprocesses; saved checkpoints remain for the next launch. This does not install an OS service. Use `scabbers --stop` once when upgrading an older detached runtime; a new panel refuses to take over an existing runtime.
- Product Epic statuses are context and remain unchanged. Feature transitions stop at Ready for Code Review; QA, Done and production are excluded. Other active engineering work still needs explicit resolution.

- Operational Tasks uses a distinct machine and two owner approvals. The initial script runtime supports local and explicit AWS account/profile/region targets; unsupported systems remain manual. Tests require Linux bubblewrap and cannot access the network, host HOME or credentials. Code review does not prove arbitrary scripts harmless. Runtime interruption after launch requires reconciliation; at-most-once automatic launch is enforced, but distributed exactly-once cloud execution is not claimed. Production execution has not been exercised in this delivery.
